# Agent Note: Agent run steer channel — multi-segment runs over journal segment rows

Status: implemented

English | [中文](2026-08-25-agent-run-steer-segments.zh.md)

## Problem

Spec 05 §5's fourth backend increment (issue #53): a follow-up to an in-progress run appends into the same task's conversation flow — no new task, and deliverables derive only from terminal `output_json`. Runs were single-segment: input at start, `submit` or failure at quiescence (the [defineAgent-compilation note](../architecture/2026-08-22-define-agent-compilation.md)'s wake contract). Four decisions were open: where follow-ups live in the ledger, when a running body consumes them, which definition kinds may be steered, and what a submit-less turn means for an opted-in run. The parked-wait mechanics reuse the [gate primitive](2026-08-23-durable-gate-waitfor.md)'s in-process push plus `pollMs` poll precedent over the [walking skeleton](../architecture/2026-08-19-daypaw-walking-skeleton.md) ledger.

## Decision

- **Segments are journal rows, not a migration** — the `journal.kind` column has no CHECK constraint, so `kind='segment'` rows land with zero migration: step key `steer:<seq>` (1-based in record order; the `steer:` prefix never collides with step keys), `occurrence=seq`, `completed` at insert, `value_json` the JSON input. Segment 0 is `runs.input_json` — an implicit boundary, never a row. A segment is a fact, not an execution unit: no re-drive re-executes it. `@daypaw/store` widens `JournalRow.kind` to the exported `JournalKindDb = 'step' | 'segment'`; the `JournalStore` seam gains `insertJournalSegment` / `selectJournalSegments`.
- **Durable-first delivery, three wakeup paths** — `DurableEngineCore.steer(runId, input)` records the row before any delivery, then pushes to a body parked in this process; a cross-process steer is observed by the parked wait's `pollMs` poll, and a segment recorded while no process drove the run is consumed by the boot-scan re-drive. Loud failures precede any write: unknown runId, terminal run, and a locally registered definition without `steerable: true` all throw plain `Error`. The call returns the 1-based segment sequence.
- **Consumption at turn boundaries, never mid-turn** — the body reads `ctx.steers()` (a plain read; consumption dedup across re-drives is the body's business) and parks with `ctx.awaitSteer(known)`, a zero-compute wait like a gate's: it returns immediately when the recorded segments already exceed `known` (check-then-wait cannot race), rejects `RUN_CANCELLED` / `ENGINE_DISPOSED` on abort or disposal, and its poll also observes rows settled by another writer. A parked run keeps the ledger status `running` — gate `waiting` semantics are untouched, and steering a gate-waiting run records without waking the gate.
- **Agent-only steerability, opt-in per definition** — `EngineDefinition.steerable?: boolean` gates `steer()`; `defineAgent({ steerable })` (default false) compiles to a segment loop. A turn that quiesces without `submit` parks the run instead of failing it; each recorded segment is delivered as a user message (`agent.steer`, JSON text, same shape as the initial input) at the segment boundary, one wake running one turn to quiescence, with `maxTurns` checked before every wake and shared across segments. Re-drive dedup counts delivered segments ordinally from the session log's `user/message` events (RESUME_MESSAGE wakes excluded — the log is the replay source, so crashes never double-deliver and identical follow-up texts stay distinct). Revival has three branches: a segment recorded while the process was dead is the wake (no synthetic RESUME_MESSAGE); a cleanly parked run re-parks without spending a turn; a crash mid-turn still wakes with RESUME_MESSAGE. `defineWorkflow` has no `steerable` option and no workflow consumption sugar — steerability is agent-only by face, and a non-steerable definition keeps the exact old semantics: a submit-less turn fails the run, so a `ctx.agent` child run cannot hang a parent workflow.
- **Wire face follows the `listDefinitions` precedent** — `DurableEngine.steer` carries `@Remote('steer')`, so the API gateway claims `durable/steer`. The Typert Remote boundary rejects unconstrained `unknown`, so the wire input is the new exported `Json` union in `packages/daypaw/engine/src/types.ts`; contract validation stays on the SDK face, where `RunHandle.steer(input)` parses against the definition's input schema before calling (`RunHandle<T, I = unknown>` gained the input type parameter).

## Alternatives considered

- **A `segments` table or a `kind` CHECK migration** — rejected: a parallel table duplicates the journal's ordering and run linkage for no new capability, and the column's missing CHECK makes the new kind free; the `steer:` key prefix keeps one ordered sequence per run without a new identity scheme.
- **Mid-turn steer injection** (interrupt the in-flight turn and re-prompt) — rejected: it races the model-visible⟺logged invariant with partial turns, spends tokens on aborted work, and dsh already delivers `agent.steer` at quiescence; turn-boundary consumption keeps one wake = one turn, which is what makes the `maxTurns` pre-wake check exact.
- **A workflow consumption primitive** (sixth ctx primitive or `defineWorkflow({ steerable })`) — rejected: no workflow caller exists, and the parent-workflow hazard runs the other way — a steerable child that never submits would hang the awaiting parent, so non-steerable definitions keep fail-on-no-submit unchanged.
- **A parked-run ledger status** (`parked` alongside `waiting`) — rejected: parked-for-steer is a wait wholly internal to the body with no external referent to name; `running` with segment rows as the observable fact keeps `RunStatus` and the presentation vocabulary unchanged.

## Consequences

A user can steer a live agent run and the run survives process death across segments: the ledger holds every input in order, the session log holds every delivered message, and the two are reconciled ordinally on revival. The SDK's typed `steer` validates before the engine is called; the engine's checks are the loud backstop for direct `ctx.durable` callers. Coverage: the fault-injection suite asserts every steer append point (segment listing, segment insert, the parked wait's poll branches, double-park rejection); behavior tests cover record order, loud failures, cross-process delivery, and boot-scan consumption of a pre-death segment; the SDK composition suite covers park-instead-of-fail, the three revival branches, and ordinal dedup; the daypaw-skeleton example proves a real-SIGKILL kill while parked revives and completes from the recorded segment. Given up: mid-turn steering (a steer waits for the current turn to quiesce), workflow steerability (no face opens it), and a distinct parked status (hosts see `running` plus segment rows). Deferred with their own demand: a workflow consumption primitive if a workflow caller appears, and any mid-turn interrupt semantics.
